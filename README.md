# Goety Codex · 诡厄巫法中文问答

面向 Minecraft 模组「诡厄巫法（Goety 1.20.1）」的 RAG 知识问答系统。
从 212 个社区页面构建 975 个知识片段（15 万字中文语料），检索 Hit@5 **85%**，
答案带可点击的来源引用，资料不足时**强制拒答**。

## 效果

70 条人工评测集（62 条有金标 + 8 条拒答），四引擎同条件对比：

| 检索引擎 | Hit@1 | Hit@5 | MRR | 检索延迟 |
|---|---|---|---|---|
| BM25（字符 bigram） | 19/62 (31%) | 38/62 (61%) | 0.433 | < 50ms |
| 向量（bge-small-zh） | 27/62 (44%) | 44/62 (71%) | 0.535 | < 100ms |
| RRF 融合 | 26/62 (42%) | 49/62 (79%) | 0.570 | < 150ms |
| **RRF + cross-encoder 重排** | **36/62 (58%)** | **53/62 (85%)** | **0.691** | 3.5s |

分类型看，重排对「概念」类（9→15）和「操作」类（6→10）提升最大；
「进度」类反而退步（3→1），因为进度表的 `名称：描述` 平铺格式不利于 cross-encoder 判断。

## 它解决什么问题

Minecraft 模组的文档是**四类异构数据**混在一起：社区 Wiki 的长文本、
游戏内结构化配方、成就树、以及玩家口语化的提问。通用 RAG 方案在这里会撞三个墙：

1. **词汇鸿沟** —— 玩家说「装上」，文档写「装备联动」；说「召不出来」，文档写「最大召唤上限」
2. **零关键词提问** —— 「放了祭品没反应」这句话里没有「仪式」「祭坛」「灵魂能量」任何一个词
3. **同类页面竞争** —— 165 个生物页面每个都有「行为模式」小节，真正该出的「通用机制」被挤下去

项目里针对这三点分别做了：领域词典改写、字符 bigram 检索、cross-encoder 重排。

## 架构

```
MCMod 网页 (212 页)  ─┐
                      ├→ 解析/清洗 → chunk × 975 ─┬→ BM25 (字符 bigram)      ─┐
jar 包 (Patchouli)   ─┘   (去重/分段/breadcrumb)   ├→ 向量 (bge-small-zh)     ─┼→ RRF → cross-encoder → top-k
                                                    └→ 查询改写 (词典/意图)    ─┘   (m3-int8)
                                                                                        │
                                        ┌───────────────────────────────────────────────┘
                                        ↓
                            LLM 生成（强制引用编号 + 资料不足则拒答）
                                        ↓
                            SSE 流式 → 单页前端（引用可点击、会话本地保存）
```

## 六个技术决策

| 决策 | 理由 |
|---|---|
| **只做中文单语** | jar 内 `zh_cn` 与 `en_us` 条目数 100% 对齐（415 = 415），无信息损失，省掉跨语言对齐 |
| **以 jar / MCMod 为权威** | 玩家实际加载的是 jar，不是 GitHub 源码；两者存在构建差异 |
| **BM25 用字符 bigram** | 「黑暗祭坛」不能被分词器切成「黑暗 / 祭坛」，否则实体匹配失效 |
| **两阶段检索** | 语料扩到 975 后同类页面互相竞争，词面和向量的排序上限都在这里 |
| **领域词典改写** | 三张表解决词汇鸿沟：动词同义（装上→装备）、语境词（开局→新手）、实体别名（笼子→诅咒之笼） |
| **强制拒答** | 资料不足必须说不知道，并指出缺什么。拒答能力比答题能力更能说明系统是否可控 |

## 快速开始

```bash
# 1. 装依赖（项目内安装，不污染全局；Windows 沙箱需要 _pip.py 绕过权限问题）
python scripts/_pip.py install --target .pylib beautifulsoup4 fastembed

# 2. 配置 API key（复制 .env.example 为 .env）
#    DEEPSEEK_API_KEY=sk-...

# 3. 建索引（首次会下载约 120 MB 模型）
python scripts/embed_index.py

# 4. 启动
python -m uvicorn server:app --port 8077
# 或 Windows 双击 run_server.bat
```

命令行版：`python scripts/chat.py`（支持多轮对话）。
离线评测：`python scripts/retrieve_hybrid.py --eval --engine all`。

## 目录

```

  fetch_*.py        抓取（jar / 单页 / 按分类批量）
  parse_mcmod.py    HTML → 结构化（小节切分、实体抽取）

  query_rewrite.py  查询理解（清洗、实体、意图、同义词）
  answer.py         生成层（prompt、引用、拒答）
kb/                 知识库产物（chunks.jsonl、vectors.npy）

docs/               工程问题记录（28 个案例，1.8 万字）
```

## 已知限制

- **覆盖率 13%**：212 / 1654 页。物品/方块分类（561 个）尚未抓取
- **进度类检索弱**：结构化表格被当纯文本处理，应还原成字段再参与排序
- **中文单语**：英文提问不适用
- **单机单进程**：未做并发压测，rerank 会占用 CPU
- **无监控**：没有日志聚合、无慢查询追踪、无失败重试
