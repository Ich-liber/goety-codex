## 二、项目里最值得讲的三件事

如果面试只问「介绍一个你最有收获的项目」，讲这三件，每件都能展开 3 分钟：

### 1. 报错位置 ≠ 根因（排查方法论）

pip 装包报 `PermissionError`，路径指向临时目录里的 whl。第一反应是修文件权限，
用诊断脚本修完**重跑仍然失败**——这一步很关键，它把「权限配置」从假设变成了排除项。

然后用十行脚本做最小复现（读写、下载、解压全正常），把范围砍到「文件写入」；
再用 `pip download` 确认失败在下载阶段；拿到栈帧 `download.py:213 open(filepath,"wb")`；
最后变量隔离发现：`tempfile.mkdtemp()` 用 `os.mkdir(name, 0o700)` 建目录，
在当前 Python 上 `mode` 会被转成**不继承父目录**的显式权限项，目录因此丢了写授权。

> 落点：**报错文本只能用来缩小范围，不能用来下结论。**

### 2. 扩数据会让指标下降（反直觉发现）

语料从 134 chunk 扩到 975 chunk（7 倍），检索指标反而从 Hit@5 25/26 掉到 23/26。
原因是新增的 165 个生物页面结构雷同，每个都有「行为模式」小节，
真正该出的「通用机制」被单个生物的小节挤下去了。

> 落点：**扩充语料提升的是覆盖率，同时会降低精度，两者不同向。**
> 所以扩完必须重新评测，不能假设变好。

### 3. rerank 有效，但上线后 40 秒（离线指标 vs 在线体验）

cross-encoder 重排把 Hit@1 从 26 提到 38，评测结果很好。上线实测首 token 要 40 秒——
20 个候选 × 全文输入，而 cross-encoder 耗时正比于输入 token 数。

两个杠杆（候选 20→12、正文截断 320 字）压到 3.5 秒，代价是 2 条准确率（38→36）。

> 落点：**离线评测只看 Hit@k，用户感知的是延迟，两个都得测。**
> 对交互式问答，超过 10 秒等待等于用户直接关页面。

## 三、面试追问准备

### Q1：为什么不用 LangChain / LlamaIndex？

**要点**：这个项目的关键工作在框架之外——HTML 结构解析、Patchouli 富文本清洗、
变体去重、领域词典、评测管线。这些用框架反而要绕开它的抽象。
框架的价值在「快速拼装标准流程」，而这里的难点是「标准流程不适用」。
自己写 2500 行，每一行都能解释为什么在那里。

### Q2：BM25 为什么用字符 bigram，不用 jieba？

**要点**：分词器会把「黑暗祭坛」切成「黑暗 / 祭坛」，实体匹配直接失效。
字符 bigram 对专有名词更稳，代价是疑问句噪声大——所以我在前面加了查询清洗。
这个取舍是实测出来的：一开始就试过通用分词，召回反而更差。

### Q3：向量模型为什么选 bge-small-zh？

**要点**：三个约束——本机没 GPU、没有 embedding API、装 torch 要拉 2.4 GB 的 CUDA 包。
所以用 fastembed（ONNX Runtime）+ bge-small-zh-v1.5，512 维、模型约 24 MB，
975 条 chunk 建索引 37 秒。效果在中文短文本检索上够用，且不依赖 GPU。

### Q4：RRF 为什么用排名不用分数？

**要点**：BM25 的分数是无界正数、余弦相似度在 [-1,1]，两者量级不可比，
加权求和要调权重且不稳定。RRF 只用排名，天然免疫尺度差异，也不需要调参。

### Q5：rerank 为什么提升这么大？

**要点**：前面两级（BM25 + 向量）都是**双塔**结构，query 和 doc 各自编码、
从不交互，只能判断「像不像」。cross-encoder 把 query 和 doc 拼在一起过模型，
能判断「这段内容到底能不能回答这个问题」。所以对于「语义相近但要选哪一条」的场景，
提升最明显——概念类 9→15、操作类 6→10。

### Q6：为什么「进度」类反而降了？

**要点**：进度表的正文是 `名称：描述；名称：描述` 的平铺字符串，
cross-encoder 读不出这种结构的价值，反而把真正相关的那条排后了。
正确的做法是把进度表还原成结构化字段（名称/描述/前置/类型）再参与排序，
而不是让模型去读拼起来的字符串。这是我已知的短板，写进 README 了。

### Q7：评测集怎么来的？会不会过拟合？

**要点**：一开始 6 条自建查询调出 6/6，然后用 30 条更口语化的重测只有 4/26——
**这就是过拟合的实证**。之后扩到 70 条（概念/操作/排错/变体/进度/拒答六类），
问题刻意口语化（「那个笼子能干什么」），gold 用 breadcrumb 子串标注。
并且承认：规则是在前 26 条上定的，所以那部分的分数偏乐观；
新增的 44 条是规则定稿后才写的，更接近真实水平。

### Q8：数据怎么来的？有什么坑？

**要点**：MCMod 是社区站，1.5 秒间隔、自定义 UA、已存在跳过。
坑有三个：(1) 变体页通过「引用于」共享同一份资料，要去重但保留 aliases；
(2) 部分页面用 `<ol>` 而不是 `<ul>`，早期解析器只处理了 `ul`，
导致「变成巫妖的三个条件」整段丢失——**这个是 LLM 回答「资料不足」时反向发现的**；
(3) 官方标题可能写错（`intro/cursed_cage` 的英文名就叫 Miscellaneous）。

### Q9：拒答怎么做的？会不会误拒？

**要点**：两层。检索层如果完全没命中就返回空；生成层的 system prompt 明确要求
「资料没有的不要用你自己的知识补充，直接说没有找到并说明缺什么」。
实测问「机械动力的齿轮怎么做」时，模型回答「资料里只有诡厄巫法的内容，
没有机械动力齿轮的配方，建议查阅 JEI」——既没编造，还指出了缺什么。
误拒的风险存在（比如资料里有但检索没召回），这是召回率问题不是拒答逻辑问题。

### Q10：这套东西的瓶颈在哪？

**要点**：三个。
(1) **覆盖率**——212/1654 页，13%。很多问题不是答不好，是根本没数据。
(2) **结构化数据**——进度表、配方这些本质是结构化字段，现在被当纯文本处理，
    信息损失在解析阶段就发生了。
(3) **单机单进程**——rerank 占 CPU，并发上来会排队，没做压测。

### Q11：如果语料扩到 10 万条，架构要怎么变？

**要点**：
- 召回层要换 ANN 索引（现在 975 条是全量矩阵乘，10 万条必须上 HNSW/IVF）
- BM25 要上倒排索引库（现在是自己实现的 dict，内存会爆）
- rerank 不能对 20 个候选做，要分层（粗排 100 → 精排 20 → 重排 5）
- 需要引入缓存（相同/相似 query）
- 要加监控：慢查询、召回率下降告警

### Q12：你觉得最大的技术难点是什么？

**要点**：不是模型，是**语料工程**。真正的坑都在数据侧：
富文本清洗错了会制造新的语义错误、`<ol>` 漏了整段条件消失、变体页重复导致检索返回两条一样的答案、
标题写错导致标题检索失效。这些没有一个能靠「换个更大的 embedding 模型」解决。

## 五、禁忌

**不要说：**

- ❌「准确率 95%」——我只有 Hit@k，没有端到端答案准确率的人工标注
- ❌「我训练了模型」——没训练，只用了预训练模型 + 检索工程
- ❌「覆盖了整个模组」——覆盖率 13%，诚实说
- ❌「做了并发压测」——没做
- ❌「用了 RAG 所以效果好」——效果来自具体决策，不是「用了 RAG」这件事本身

**应该说：**

- ✅「Hit@5 85%，Hit@1 58%，这是检索层指标，端到端答案正确率我没做大规模人工标注」
- ✅「覆盖率 13%，瓶颈在数据不在模型」
- ✅「这个方案在 975 条语料上验证过，10 万条要换 ANN 索引和倒排库」
