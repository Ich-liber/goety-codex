## 一、环境与工具链

### 1. Windows 下 HTTP 下载失败

**现象**

```
Invoke-WebRequest : 基础连接已经关闭: 接收时发生错误
curl: (35) schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030E)
```

PowerShell 和 curl 两个工具都下不了 96 MB 的 jar。

**根因**

Windows 上 `Invoke-WebRequest`（.NET）和 `curl.exe` 默认都走 **schannel**——Windows 自带的 TLS 实现，需要从凭据管理器取一个句柄。在受限环境里拿不到，于是在握手前就失败，报的是"凭据"而不是"证书"或"连接"。

**处理**

改用 Python `requests`，它走 **OpenSSL** 栈，不依赖 Windows 凭据服务。一次成功，1.2 MB/s。

**面试怎么讲**

> 同一个下载任务，换 TLS 后端就通了。这说明"网络请求失败"未必是网络问题，也可能是 TLS 实现依赖了当前环境拿不到的系统资源。排查时先区分「应用层错误」和「系统凭据层错误」。

### 2. ★ pip 安装报 PermissionError（核心案例）

**现象**

```
ERROR: Could not install packages due to an OSError: [Errno 13] Permission denied:
'E:\...\goety-rag\.tmp\pip-unpack-u9w5s0s9\beautifulsoup4-4.15.0-py3-none-any.whl'
```

任何包都装不上（`pip install` 和 `pip download` 都失败），而同一目录下手写文件却完全正常。

**排查过程（五步，这是重点）**

1. **先怀疑权限项**：用诊断脚本检查失败路径和它的每一级祖先目录，发现 `goety-rag` 和 `.tmp` 缺 `WRITE_OWNER`，脚本修复并验证通过。→ **重跑，仍然失败**。
   *这一步排除了权限项配置问题，价值极高：它把"权限问题"从假设变成"已排除"。*

2. **最小复现**：写十几行脚本，测普通写读、`requests` 下载、`zipfile` 读取、`chmod`——**全部正常**。
   *这一步排除了"沙箱普遍限制文件写入"。*

3. **隔离阶段**：`pip download`（只下载不安装）也失败，且目标目录为空。→ 问题在**下载写入**阶段，不在解压安装阶段。

4. **拿到精确栈帧**：加 `-v` 后定位到
   ```
   pip/_internal/network/download.py:213  in __call__
       with open(filepath, "wb") as content_file:
   PermissionError: [Errno 13]
   ```
   就是一个最普通的 `open(path, "wb")`。

5. **变量隔离实验**（决定性一步）：

   | 创建方式 | 结果 |
   |---|---|
   | `os.makedirs(路径)` | ✅ 可写 |
   | `os.mkdir(路径, 0o700)` 新建 | ❌ 不可写 |
   | `tempfile.mkdtemp()` 新建 | ❌ 不可写 |
   | `tempfile.mkdtemp(prefix="pmt")` | ❌ 不可写 |

   最后一个实验是为了排除"目录名以 tmp 开头"这个干扰变量。剩下的唯一差异就是 **mode 参数**。

**根因**

`tempfile.mkdtemp()` 内部是这么写的：

```python
os.mkdir(name, 0o700)
```

而当前 Python 环境（3.14）在 Windows 上会把 `mkdir` 的 `mode` **转换成显式权限项**。显式权限项**不继承父目录的授权**，于是新建的临时目录丢失了工作区授予的写权限。

最阴险的一点：`os.stat()` 报出来的 mode 仍是 `0o40777`，看起来完全可写——**权限位正常，实际 DACL 里没有当前用户**。这就是"看权限位没问题，写却失败"的原因，也是我第一次误判的直接诱因。

**处理**

写了一个 pip 兼容启动器 `scripts/_pip.py`，在导入 pip 前替换 `os.mkdir`，丢弃 `mode` 参数，恢复权限继承：

```python
_orig_mkdir = os.mkdir

def _mkdir_inherit(path, mode=0o777, *, dir_fd=None):
    if dir_fd is not None:
        return _orig_mkdir(path, mode, dir_fd=dir_fd)
    return _orig_mkdir(path)      # 不传 mode -> 走默认流程 -> 继承父目录 ACL

os.mkdir = _mkdir_inherit
runpy.run_module("pip", run_name="__main__")
```

之后 `bs4`、`soupsieve`、`typing-extensions` 全部正常安装。

**面试怎么讲（这段最值得展开）**

- **报错位置 ≠ 根因**：报错在 pip 的 `open()`，根因在两层调用栈之外的 `tempfile.mkdtemp()`。
- **被关键词误导**：看到 `Permission denied` 就本能去修权限，方向其实错了。正确的判断依据不是错误文本，而是**对照实验**。
- **最小复现的价值**：如果一上来就怀疑 pip 自己的 bug 或者沙箱策略，会浪费大量时间；十几行脚本就把范围砍到了"文件写入"这一层。
- **变量隔离**：并行验证 mode 参数、目录名、创建方式三个变量，才锁死到唯一原因。
- **兼容层的写法**：不 fork pip、不改 site-packages，用一个薄启动器 monkey-patch，可复现、可删除、不污染全局。

### 3. venv 建好了却没有 pip

**现象**

```
python -m venv .venv
→ Error: Command '[.../python.exe', '-m', 'ensurepip', ...]' returned non-zero exit status 1
→ No module named pip
```

**根因**

同源问题：`ensurepip` 也要写临时目录、并且要往沙箱外的 `site-packages` 安装。

**处理**

放弃 venv，改用 `pip install --target .pylib` + `PYTHONPATH`，所有产物落在工作区内。

**面试怎么讲**

> 受限环境里，"依赖装在项目内 + 显式 PYTHONPATH"比"装到系统或 venv"更可控，也更容易复现和清理。

### 4. pip 的临时目录也必须在可写区域内

**现象**

只设置 `--target` 不够，pip 仍去系统 `%TEMP%` 下报错。

**处理**

三个写入点一起改：

```powershell
$env:TEMP = "$root\.tmp"; $env:TMP = "$root\.tmp"
$env:PIP_CACHE_DIR = "$root\.tmp\pip-cache"
```

**面试怎么讲**

> pip 有三个写入点：临时解包目录、HTTP 缓存、安装目标目录。只改一个不够，要一起纳管。

### 5. Windows 控制台中文乱码

**现象**：Python 输出中文变问号或乱码。

**处理**：脚本内自带兜底，不依赖调用方设置：

```python
try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass
```

运行时再加 `PYTHONIOENCODING=utf-8`。

**面试怎么讲**

> 工具脚本要能独立运行，不能假设调用方已经设置好编码环境。

---

### 6. PowerShell 内联 Python 的引号地狱

**现象**

`python -c "...f'{getattr(mod,\"__version__\")}'..."` → `SyntaxError: unterminated string literal`

**处理**：改用 here-string，避免 shell 和 Python 两级转义：

```powershell
@'
import bs4
print(bs4.__version__)
'@ | python -
```

**面试怎么讲**

> 超过三行的 Python 一律落成文件；`-c` 只用于真正的单行命令。

### 7. 每次 shell 调用都是新进程

**现象**

`python scripts\_pip.py ...` 报 `can't open file 'E:\...\deepseekpro\scripts\_pip.py'`——相对路径被解析到了工作区根，而不是项目目录。

**处理**：全部用绝对路径，或显式传 `workdir`。

**面试怎么讲**

> 自动化脚本不要假设 cwd；跨步骤的状态（环境变量、工作目录）在新进程里都会丢。

## 二、数据获取

### 8. GitHub raw 域名不可达

**现象**：`raw.githubusercontent.com` 报 `TypeError: fetch failed`。

**处理**：改走 `api.github.com/repos/.../contents/...`，响应里 `content` 字段是 base64，自行解码。

**面试怎么讲**

> 抓取前先确认"哪条通道在当前网络下可用"。raw 域名和 api 域名常常走不同链路，API 还附带元数据（sha、size），比 raw 更适合做校验。

---

### 9. 超大 API 响应被截断

**现象**

`git/trees/1.20?recursive=1` 返回整个仓库几万个文件，落盘后只保留了首尾约 100 KB，中间被省略。据此统计出"350 个 blob"这个明显错误的数字。

**处理**：放弃全量 tree，改为逐个访问目标子目录（`contents/...`），对每个响应的完整性单独校验。

**面试怎么讲**

> 对"大小不确定"的响应要做窄化查询或分页；更重要的是**统计之前先确认数据完整性**——否则会得到看似合理但完全错误的数字。我当时差点用 350 这个数字下结论。

---

### 10. MCMod 的礼貌抓取

**做法**

- 单线程 + 固定 1.5 s 间隔
- 自定义 UA 明确标识用途：`goety-rag-research/0.1 (personal non-commercial study)`
- 已存在文件跳过，支持重复运行
- 抓完即落盘，不反复请求

**面试怎么讲**

> 抓社区站点要有速率限制和身份标识。这不是"怕被封"，而是基本的工程伦理——你的项目不该给别人造成成本。顺带也是简历上的加分细节：知道 MCMod 内容是 BY-NC-SA 3.0，只在非商业场景使用并署名。

## 三、数据质量（RAG 项目真正的难点）

### 11. Patchouli 富文本标记污染索引

**现象**

jar 里的官方手册文本长这样：

```
$(l:intro/cursed_cage)Cursed Cage$()
```

还有 `$(br)`（换行）、`$(l)斜体$()` 等标记。

**根因**

最开始我写了个 `strip_rt()` 直接正则删掉所有 `$(...)`。结果 `$(br)` 也变成空字符串，相邻句子直接粘连：

```
"…向周围溅射酸液 使用魔杖施法时…"     ← 中间本该是换行/句号
```

**处理**

清洗的目标不是"删掉标记"，而是"把标记翻译成结构"：

- `$(l:target)文字$()` → `{"text": "文字", "link": "target"}`，既清洗噪声又顺手抽出了文档间边
- `$(br)` → 标点或换行，不能留空
- `$(l)…$()` 等纯格式标记 → 只保留文字

**面试怎么讲**

> 错误清洗会制造新的语义错误。`$(br)` 被删掉后，句子粘连会让 embedding 的语义完全变形——这类问题在指标上表现为"检索莫名其妙不准"，很难倒查。所以清洗管道必须对每一种标记都明确"翻译成什么"，而不是"统一删掉"。

---

### 12. 标题与内容不匹配

**现象**

`intro/cursed_cage.json` 的 `name` 字段，英文原文是 `Miscellaneous`（杂项），中文译成"混杂之音"，但正文讲的是**诅咒之笼**。

**根因**

不是翻译错误，是**作者源数据本身就没写对标题**（中英同错，说明是从英文错误翻译过来的）。

**处理**

chunk 必须保留正文，标题只作辅助信号，绝不能"只索引标题"。

**面试怎么讲**

> 这是"不能依赖单一字段"的实证。如果架构上把标题当主键或做标题过滤，这类条目会直接检索不到。也说明为什么文档分块要保留完整正文 + breadcrumb，而不是抽关键词。

---

### 13. 变体爆炸

**现象**

单个「黑暗祭坛」在 MCMod 上有 10+ 个独立页面（`751714`、`894582`–`894588`、`935699`、`935700`…），它们外观不同、功能完全相同。

**处理**

按 tag 聚合为"文档组"。这些页面共享 `goety:dark_altars`，tag 就是官方的归并答案——不用自己发明规则。回答时说明"有 N 种外观，功能相同"。

**面试怎么讲**

> 检索歧义不只来自语义相似，还来自"同一实体被拆成多个条目"。如果不聚合，用户问"黑暗祭坛有几种外观"会拿到 10 个几乎一样的答案。而解法不用猜——游戏本身就有 tag 体系，直接用它。

---

### 14. 中英条目完全对齐，但仍有英文残留

**现象**

- Patchouli：`zh_cn` 415 条 = `en_us` 415 条，**零缺失、零未翻译**（我用中英 name 逐条比对，0 条相同）
- 但 `lang/zh_cn.json` 里有 25 条值仍是英文

**处理**

逐条看内容后判断为**专有名词**，不需要处理：

```
item.goety.music_disc_vizier.desc = Peter Hont - Evoker
painting.goety.capstone.title     = Capstone Room
```

**面试怎么讲**

> 质量指标不能只看比例。如果机械地要求"中文文件汉字占比 100%"，会误伤音乐唱片名、画作名这类本就不该翻译的内容。判断质量要看**内容类型**，不是单一阈值。

---

### 15. jar 与 GitHub 源码不一致

**现象**

从 GitHub 源码树估算 Patchouli 条目约 407 条；实际解包 jar 得到 415 条（含 `witches_brew` 8 条）。

**处理**

**以 jar 为权威**，源码只作参考。

**面试怎么讲**

> 发布产物和源码仓库存在差异是常态（构建裁剪、datagen 生成、分支状态不同）。对 RAG 来说，**玩家实际加载的是 jar**，所以知识库必须和运行时分发物对齐，而不是和仓库对齐。这个决策会直接影响答案的事实正确性。

## 四、解析实现细节

### 16. `get_text(" ")` 在链接两侧注入空格

**现象**

```python
node.get_text(" ", strip=True)
```

会把 `<a>` 前后的分隔符也插进去，得到：

```
"组成 魔法仪式 的核心方块"       ← 中文里不该有这些空格
```

**处理**

```python
re.sub(r"(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])", "", text)
```

只清理汉字之间的空格，保留中英之间的必要间隔。

**面试怎么讲**

> HTML 解析器的分隔符参数会直接影响文本质量，而中文对空格敏感。中文 NLP 管道里凡是"拼接文本"的地方都要单独考虑。

### 17. legend 自引用污染实体关系

**现象**

从正文抽内链构建实体关系时，第一条永远是页面自己（"黑暗祭坛 (Dark Altar)" → 自己的 id），因为它来自 `<legend>` 里那句"此段资料引用于…"。

**处理**：抽取时跳过 `<legend>` 内的链接。

**面试怎么讲**

> 关系抽取要排除自指和导航性链接（面包屑、引用声明、页脚）。否则"实体图"里会充满自己指向自己的噪声边。

### 18. MCMod 正文没有语义标题标签

**现象**

页面里**没有** `h2`/`h3`，小节标题长这样：

```html
<p><span>激活</span></p>
<p>要使用黑暗祭坛，首先需要激活它…</p>
```

纯靠视觉样式区分，语义上就是普通段落。

**处理**

启发式识别：`<p>` 只有一个 `<span>` 子元素、且该 span 文本很短（≤ 20 字）→ 判定为小节标题。

**面试怎么讲**

> 爬虫要适应"人类看得出、机器看不出"的结构。这类启发式规则必须可验证——我的做法是先把整页的元素序列打出来人工确认，再写规则，而不是拍脑袋。

### 19. 统计口径差异

**现象**

- 按 `*.json` 统计 recipes：**1655**
- 按 `recipes/` 目录下所有文件统计：**1697**

**处理**：明确口径，报表里写清"json 文件数"。

**面试怎么讲**

> 数据报表必须注明口径。否则同一份数据在不同脚本里跑出两个数字，后面会反复怀疑自己。

## 五、检索基线

### 20. 正文容器选错，28 个页面只抓到 2 个正文

**现象**

第一版解析器把 `fieldset.quote_text` 当作正文容器——因为它在我最先看的那个页面（黑暗祭坛）里正好存在。结果 28 个样本里**只有 2 个**提取到正文，总字数仅 1,840；同时「提及物品」抓到了 **842 个**链接，因为容器取不到时代码 fallback 到了整个页面。

**根因**

`fieldset.quote_text` 只出现在「引用其它页面」的条目里。普通页面的正文直接挂在 `div.item-content` 下（`p` / `ul` / `table` 是直接子元素），没有 fieldset 包裹。

**处理**

统一用 `div.item-content`；若其内部有 `fieldset.quote_text`，则下沉一层并跳过 `legend`。修复后：有小节的页面 2 → 28，正文 1,840 → 26,120 字。

**面试怎么讲**

> 这是「样本量为 1」的代价。我看了一个页面就总结出选择器，而它恰好是特例。垂直切片的价值就在这里：20 多个页面立刻暴露问题，而不是抓完 1600 页才发现。经验是 **选择器至少要在 3 种不同页面类型上验证过**才能定稿。

---

### 21. 变体页内容重复，检索返回两条一样的答案

**现象**

查询「黑暗祭坛怎么激活」时，top1 和 top2 是同一段文字，分数完全相同。

**根因**

`935700` 和 `894598` 是两个「黑暗祭坛」变体页，但 MCMod 用的是**「引用于…并与其保持同步更新」**机制——多个变体页共享同一份资料，不是各自维护。5 个小节全部重复。

**处理**

按 `(标题, 小节名, 正文)` 去重，保留一条；被合并的页面 id 记入 `aliases` 字段，留给「有几种外观」这类聚合问题用。

**面试怎么讲**

> 去重不能只看 id 或 URL，要看内容；但也不能纯粹按内容去重——比如「僵尸&骷髅类仆从通用机制」和「常规仆从通用机制」两个不同标题共享同一份正文，删掉一个会让用户搜不到另一个入口。所以规则是：**同标题同内容才合并，标题不同则保留，关系记进 aliases**。

### 22. BM25 基线被疑问词带偏

**现象**

6 条测试查询（覆盖概念 / 操作 / 排错 / 多跳）里，**top1 只命中 2 条**：

| 查询 | 类型 | top1 | 是否正确 |
|---|---|---|---|
| 灵魂能量怎么获得 | 概念 | 灵魂能量 > 玩家的灵魂能量槽 | ✅ |
| 黑暗祭坛怎么激活 | 操作 | 黑暗祭坛 > 激活 | ✅ |
| 我的仪式放上祭品却没有反应 | 排错 | 巫妖 > 开启 | ❌ |
| 聚晶有什么用 | 概念 | 使徒 > 姓名与头衔 | ❌ |
| 红石傀儡怎么召唤 | 多跳 | 红石傀儡 > 相关进度表 | △ |
| 巫妖有什么好处 | 概念 | 使徒 > 姓名与头衔 | ❌ |

**根因**

字符 bigram 不看词性。「有什么用」被拆成 `有什 / 什么 / 么用`，其中「什么」在大量 chunk 里出现，而「有」字给了一段完全无关的文本不该有的分数。IDF 压不住——这些字在 141 个 chunk 里的出现频次还不够高。

**处理（待做）**

查询理解阶段剥离疑问词与意图词（怎么 / 如何 / 有什么用 / 为什么 / 有什么好处），只保留实体和动作。

**面试怎么讲**

> 这是字级检索的边界。bigram 对专有名词很友好（不会把「黑暗祭坛」切碎成「黑暗/祭坛」），但对疑问句很糟糕。所以混合检索不是「向量 + BM25 加权平均」这么简单——**前置的查询清洗往往比后面的融合策略收益更大**。这条 2/6 的基线也是后面消融实验的起点。

### 23. 查询清洗：3/6 → 6/6，以及三次失败的尝试

**最终消融结果**（6 条查询，k=5）

| 配置 | top1 | top5 |
|---|---|---|
| raw 原查询 | 3/6 | 5/6 |
| + 查询清洗 + 实体识别 + 症状扩展 | 4/6 | 6/6 |
| + 标题加权 ×2 | 4/6 | 5/6 ↓ |
| + 意图扩展（所有意图） | 4/6 | 6/6（howto 类掉到 #2） |
| **+ 意图扩展（仅 concept）** | **6/6** | **6/6** |

**第一次失败：单字停用词把词拆坏了**

把「得」放进停用词表后：

```
灵魂能量怎么获得  →  灵魂能量 获      ← 「获得」被拆成「获」
```

中文没有词边界，单字停用词做子串删除必然误伤复合词（得/获得、的/目的、了/了解）。
**改为只收多字停用词 + 按长度降序删除**，单字交还给 BM25 的 IDF 自然降权。

**第二次失败：标题加权反而让指标下降**

我以为「标题信号没进索引」是问题，于是把 `title + heading` 重复两次拼进索引文本。结果「巫妖有什么好处」从 #3 直接掉出 top5。

原因有两层：

1. 同一物品的所有 chunk **共享同一个 title**（都是「巫妖」），加权对这个实体毫无区分度；
2. 加权把文档变长了，触发 BM25 的长度归一化惩罚——短 chunk 本来靠“短”占便宜，现在被拉长。

真正有区分度的是 `heading`（「特点」vs「巫妖之吻」），不是 `title`。这个改动已撤回。

**第三次失败：意图扩展不能全开**

给所有意图都配扩展词后，concept 类被救回 #1，但 howto 类掉下去了：

```
灵魂能量怎么获得 → 灵魂能量 获得 获取 制作 激活 方法   → 从 #1 掉到 #2
```

原因是「获取/制作/激活/方法」这类泛词在很多 chunk 里出现，稀释了「灵魂能量 + 获得」的精确匹配。

**最终规则：只给 concept 扩展。**

这个规则有解释力：concept 型查询问的是**类别属性**（“有什么用”“什么好处”），实体名本身定位不到『特点』这类小节；而 howto / multihop 查询**自带动作词**（获得、召唤、激活），再扩展只是加噪。

**过拟合警告**

6 条查询是我自己写的，gold 也是我标的，这个 6/6 **不能当作最终指标**。真实评测集需要 150 条以上、来自真实玩家提问，并且要在这套规则定稿之前采样，否则等于用测试集调参。

**面试怎么讲**

> 做查询清洗时我先失败了三次：单字停用词把「获得」拆成了「获」；标题加权反而让指标下降，因为同物品所有小节共享同一个标题，既没区分度又拉长了文档；意图扩展全开时，泛词把精确匹配稀释了。
>
> 最后收敛出的规则是**只给 concept 型查询扩展**——因为它问的是类别属性，实体名定位不到目标小节；而 howto 型自带动作词，扩展只会加噪。这个过程让我更相信一件事：**查询改写是收益最高也最容易过拟合的环节，每加一条规则都必须有成对的反例验证。**

### 24. 用 30 条真实提问重测：6/6 掉到 4/26

**上一节的 6/6 是过拟合的实证**

上一节那 6 条查询是我自己写的、gold 也是我标的、规则就是在它们上面调出来的。为了验证，我另外造了 **30 条刻意口语化**的评测集（`eval/qa_set.jsonl`，6 类：概念 / 操作 / 排错 / 变体 / 进度 / 拒答），再测一次：

| 模式 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| raw | 3/26 | 16/26 | 0.290 |
| rewrite | 4/26 | 17/26 | 0.353 |

**6/6 掉到 4/26。** 这就是为什么自建小样本不能当指标——它不是"差一点"，是完全不同量级。

**第一次修：进度表字段名是噪声源**

「相关进度表」chunk 原本这样拼的：

```
名称：战争铸造；描述：用活力核心召唤红石傀儡；需求：召唤红石傀儡；类型：目标；父进度：沉重但无意义；是否在聊天栏显示：是；ID：goety/summon_redstone_golem；是否隐藏：否；经验：0
```

`名称 / 需求 / 类型 / 父进度 / 是否隐藏 / 经验` 这些**字段名**在 21 个 chunk 里重复出现，对自然语言查询吸引力极强，却没有信息量。查询「刚开局做什么」会被这些通用词拉到随便一张进度表上。

处理：只保留「名称」和「描述」的值，字段名全部丢弃。chunk 数 141 → 131（10 个空表被跳过）。

**第二次修：实体识别了却没用来过滤**

查询「聚晶怎么装上」返回「黑暗魔杖 > 概述」——明明识别出实体「聚晶」，却让一个跟聚晶毫无关系的段落因为讲施法而上位。

处理：实体命中时，**先把候选限定在该实体的 chunk 内再排序**（title 包含实体名）。候选不足 2 个或全部零分则回退全局检索，避免过滤过狠。

**第三次修：领域词典**

诊断失败 case 后发现三类词面缺口：

| 查询 | 缺口 | 类型 |
|---|---|---|
| 那个笼子能干什么 | 「诅咒之笼」的尾词是「之笼」，匹配不到「笼子」 | 实体别名 |
| 聚晶怎么装上 | 「装上」永远匹配不到「装备联动」 | 动作同义词 |
| 刚开局做什么 | 字面上没有任何词能连到「新手工具」这条进度 | 语境词 |

补了三张表：`VERB_SYNONYMS`（装上→装备、攒→获得、弄→制作…）、`GENERIC_EXPANSION`（开局/前期→新手/入门/进度）、`ENTITY_ALIASES`（笼子→诅咒之笼，只收指向明确的）。

**最终结果**

| 模式 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| raw | 3/26 | 16/26 | 0.296 |
| rewrite | **13/26** | **23/26** | **0.652** |

| 类型 | raw | rewrite |
|---|---|---|
| 概念 | 0/6 | 3/6 |
| 操作 | 1/7 | 3/7 |
| 排错 | 0/7 | **1/7** |
| 变体 | 2/3 | 3/3 |
| 进度 | 0/3 | 3/3 |

**剩下的瓶颈很清楚：排错型 1/7。**

四条仍失败的都是纯语义问题，词典补不动：

- 「傀儡召不出来」→ 该去「最大召唤上限」，却落到「分散红石地雷」
- 「聚晶装上了不能用」→ 该去「装备联动」，却落到「功能」
- 「药酿怎么弄」→「药酿」本身是歧义词（药酿包 / 药酿机制 / 基础效果）

这类需要**语义检索**（embedding），字符匹配和同义词表都到顶了。

**面试怎么讲**

> 我先用 6 条自建查询调出 6/6，然后立刻用 30 条更口语化的评测集打回来，只有 4/26。这一步很关键——它证明了自建小样本的指标不可信，也让我把"调参"和"验证"分开了。
>
> 之后三步修复把 Hit@5 从 17/26 提到 23/26：清掉进度表的字段名噪声、让实体识别真正参与候选过滤、补三张领域词典。但排错型始终卡在 1/7，说明**字符匹配加同义词的天花板就在这里**，剩下的是语义问题，必须上向量检索。

### 25. 生成层的「资料不足」反向暴露了解析缺陷：`<ol>` 被整段丢弃

**现象**

端到端测试跑第一条「变成巫妖有啥好处」，模型的回答末尾写了这么一段：

> 至于「变成巫妖的具体条件」，资料 [3] 只写了「必须满足以下的条件」，但条件列表本身没有给出，现有资料里没有找到相关内容。

模型没有编造条件，而是如实报告资料缺失。这句话直接指向了数据管道的缺陷。

**根因**

`parse_sections` 只处理了 `<ul>`，漏了 `<ol>`。而 MCMod 的「条件」「步骤」类小节偏偏用的是有序列表。

查页面结构确认：

```
item-content 子元素类型统计: {'p': 38, 'ol': 1, 'ul': 1, 'script': 1}
发现 <ol>，共 3 项:
   - 有一个已经绑定的 灵魂方舟 。
   - 时间必须是满月的夜晚，如果你不想等待，自然也有 捷径 。
   - 做好死亡的准备。
```

三个条件全被跳过了。更糟的是，它留下了一个诡异的残留小节 `× 25`——那是列表被丢弃后剩下的碎片，之前我还以为是什么装饰符号。

**处理**

```python
elif name in ("ul", "ol"):   # 原来只判断 "ul"
```

修复后：「巫妖 > 条件」从 **56 字 → 125 字**，三个条件完整；`× 25` 这个假小节自然消失；全库正文 26,120 → 26,965 字。

**面试怎么讲**

> 这个 bug 是 LLM 帮我发现的。它没有硬答，而是说「资料里只有一句『必须满足以下条件』，列表本身没有」。我顺着这句话去查 HTML，才发现解析器只处理了无序列表，把有序列表整段丢了。
>
> 这让我对评测顺序有了新认识：**检索指标看不出「内容残缺」**。这个 chunk 在检索层是「命中」的——它确实被检索到了、也进了上下文，Hit@1 完全正常。只有到了生成层，模型发现它讲不完整，问题才暴露。
>
> 所以 RAG 的评测不能只有检索指标，**「生成层诚实地承认不知道」本身就是一种数据质量的探针**。反过来讲，如果一个 RAG 系统从来不承认不知道，它的数据缺陷就永远浮不上来。

### 26. 多轮上下文用过头，反而污染了独立话题

**现象**

给 CLI 加上多轮对话后，第一轮「变成巫妖有啥好处」正常，第二轮「那要怎么变呢」也能正确结合上文。但第三轮「傀儡召不出来」突然答不出来了——模型说「现有资料里没有找到相关内容」。

而同样的问题在单轮测试里是能答对的（会命中「红石傀儡 > 最大召唤上限」）。

**根因**

当时的规则是**「查询短于 12 字就拼接上一轮问题」**。

「傀儡召不出来」只有 6 个字，于是检索查询被拼成了：

```
那要怎么变呢 傀儡 召唤 上限
```

上一轮的「巫妖/转化」语义把检索拽走了，红石傀儡的片段被挤出了候选集。

**处理**

判断条件从「长度」改成「是否真的需要上文」：

```python
ANAPHORA = ("那", "这个", "那个", "它", "它们", "怎么变", "然后", "还有", "上面", "刚才", "呢")

def needs_context(q, entities):
    if len(q) > 12:
        return False
    if any(w in q for w in ANAPHORA):   # 有指代词
        return True
    return not entities                  # 或者整句没有任何实体
```

修复后：「那要怎么变呢」带 `+上文` 标记、正确借用上文；「傀儡召不出来」因为含实体「傀儡」且无指代词，不再拼接，恢复正确。

**面试怎么讲**

> 多轮对话是双刃剑。我一开始用「短查询就拼上文」这种简单规则，结果把一个独立的新问题污染了——因为短不代表依赖上文，它可能只是问得简洁。
>
> 真正的判断依据应该是**有没有指代**，而不是**有多短**。这件事让我把「上下文增强」和「上下文污染」明确分开了：拼接前先问一句「这句话离开上文还成立吗」，成立就不该拼。

### 27. 语料翻 7 倍，指标反而下降

**现象**

按分类批量补抓（生物 165 + 多方块 15 + 游戏设定 18）后，知识库从 27 页涨到 212 页、134 chunk 涨到 975：

| | 扩之前 | 扩之后 |
|---|---|---|
| chunk | 134 | 975 |
| 正文 | 26,642 字 | 149,704 字 |
| RRF Hit@5 | 25/26 | **23/26** |
| RRF MRR | 0.722 | **0.674** |

数据变多，效果变差。

**根因**

新增的 165 个生物页面结构高度雷同，每个都有「行为模式」「生成」「战斗行为」「嘲讽机制」这些小节。查询「仆从模式怎么切」时，候选里同时出现：

```
常规仆从通用:基础机制与模式切换 > 行为模式   ← 想要的（通用机制，讲全部仆从）
僵尸猪灵蛮兵仆从 > 行为模式                  ← 抢走排名的（单个生物）
```

「怎么变巫妖」被「巫妖 > 琐事」抢走也是同理：同实体的多个小节在争同一个词。

**这说明一个反直觉的事实**：扩充语料提升的是**覆盖率**，同时会**降低精度**。两者不是同向的。

**面试怎么讲**

> 很多人默认「数据越多效果越好」。我这次扩了 7 倍语料，检索指标反而掉了。原因是新增内容和已有内容高度同构，每个生物都有自己的「行为模式」小节，它们把真正该出的那条通用机制挤下去了。
>
> 所以扩数据之后必须重新评测，不能假设变好。而且这暴露出词面匹配和向量检索的上限：它们能判断「像」，判断不了「哪个更该回答这个问题」。

### 28. cross-encoder 重排：Hit@1 提升 10 条，代价是 40 秒延迟

**引入**

面对上面那个问题，加了第二阶段检索：RRF 先召回 12–20 个候选，再用 `bge-reranker-v2-m3-int8`（cross-encoder）逐对打分重排。模型只有 0.57 GB，走 ONNX，不需要 torch。

**效果**（62 条有金标的评测集）

| 引擎 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| BM25 | 19/62 | 38/62 | 0.433 |
| 向量 | 27/62 | 44/62 | 0.535 |
| RRF | 26/62 | 49/62 | 0.570 |
| **Rerank** | **36/62** | **53/62** | **0.691** |

Hit@1 从 26 提升到 36（+16 个百分点），Hit@5 到 85%。分类型看，概念类 9→15、操作类 6→10，提升最明显——正是那些「语义相近但要看具体哪条」的问题。

唯一退步的是「进度」类（3/4 → 1/4）：进度表的正文是 `名称：描述；名称：描述` 的平铺格式，cross-encoder 读不出这种结构化的价值。

**代价：首 token 40 秒**

上线后实测，单次查询首 token 要 **40.5 秒**。定位到 cross-encoder 是唯一瓶颈（LLM 生成只占 1 秒）。

原因是两个乘法：
1. 候选数 20 个，每个都要做一次 query-doc 推理；
2. 送入的是 chunk 全文，长的有 1578 字，token 数直接决定推理时间。

**优化**

- 候选从 20 降到 12（`max(k*3, 12)`）
- 文档截断到 320 字（保留 breadcrumb，砍掉长尾）

结果：**40.5 秒 → 3.2–3.7 秒**，12 倍提速。代价是指标轻微下降：

| | 优化前 | 优化后 |
|---|---|---|
| Hit@1 | 38/62 | 36/62 |
| Hit@5 | 55/62 | 53/62 |
| MRR | 0.721 | 0.691 |

**面试怎么讲**

> 加 rerank 之后效果确实上去了，Hit@1 提了 16 个点。但上线实测首 token 要 40 秒——完全不可用。
>
> 排查发现瓶颈全在 cross-encoder：20 个候选 × 全文输入。因为 cross-encoder 的耗时正比于输入 token 数，所以两个杠杆——减少候选数、截断文档——直接把 40 秒压到 3.5 秒。
>
> 这里有个权衡：牺牲了 2 条准确率（38→36）换 12 倍速度。我认为值，因为对交互式问答来说，超过 10 秒的等待会让用户直接关掉页面。
>
> 这件事也说明**离线评测和在线体验是两个指标**。评测只看 Hit@k，但用户感知的是延迟。两个都得测。

## 附：三条主线怎么用

**面试讲 §2 时**，落脚点不是"我修好了 pip"，而是：

> 我遇到一个报错位置和根因相隔两层的 bug。我先用对照实验排除了权限配置和沙箱策略，再用最小复现定位到文件写入层，最后通过变量隔离发现是 `mkdir` 的 `mode` 参数破坏了权限继承。这个案子让我确认了一件事：**报错文本只能用来缩小范围，不能用来下结论。**

**面试讲 §11–15 时**，落脚点是：

> RAG 的效果瓶颈通常不在模型，而在语料。我遇到的三个典型缺陷是：富文本标记被错误清洗导致句子粘连、官方标题写错导致标题检索失效、同一实体被拆成 10 个条目导致检索歧义。这些都不是"换个更大的 embedding 模型"能解决的。

**面试讲文末取舍时**，落脚点是：

> 小语料项目的优势在于可以承担更多工程成本。比如我坚持以 jar 而不是 GitHub 源码为权威数据源，因为玩家加载的是 jar；比如我用游戏自带的 tag 做变体归并，而不是自己定规则。这些判断依赖对领域的理解，不是通用框架能提供的。
